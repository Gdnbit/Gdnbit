# Dynamic Interview & Verification Guide

Generate interview questions from the **current JD**, **the actual project/repository chosen for review**, and **material evidence gaps**. This is a question-generation method, **not** a fixed bank tied to past repository names.

## 1. Choose what to test

Extract the role's key expected responsibilities and required level. Depending on the role, prioritize:

- Business-to-system translation: ambiguity, business entities, rules, user states and acceptance criteria.
- Product judgment: actual user pain, prioritization, first-version scope, iteration from feedback.
- Agent workflow: context, tools, model boundaries, human approval, predictable vs model decisions.
- Engineering comprehension: contracts, data model, failure modes, security, tests, debugging and deployment.
- AI-assisted implementation ownership: specification, delegation, code review, debugging and acceptance.
- Delivery and collaboration: communication, handoff, constraints, trade-offs, team contributions and operations.

Not every role needs deep algorithmic coding, sales-led discovery or infrastructure operations. Test the **job**, not a generic idealized engineer.

## 2. Generate questions from observable evidence

For each high-impact requirement:

1. Pick the most relevant **current** project or real-work example.
2. Inspect its current README/status and the specific implementation paths needed.
3. Form a hypothesis about the relevant candidate capability.
4. Identify the **strongest evidence** and what remains unknown.
5. Ask a question where a concrete answer or walkthrough could confirm or disconfirm the hypothesis.
6. Define what a strong, mixed and weak answer would look like.

Example pattern (substitute any current project):

> "You describe [workflow/capability]. Show the exact path from [input] to [stored state/output], including a failure case. Which decisions were yours, which were adapted from upstream, and which were generated by Coding Agents? How did you verify the behavior?"

Do not ask about a feature unless evidence suggests it exists or the question is explicitly a hypothetical design test.

## 3. Focused question families

### Business-to-system design

- Which requirements already existed before you joined, and which ambiguities did you personally resolve?
- Identify the main users, entities, fields, states, permissions and exceptional paths.
- Show how a vague rule became observable UI, data constraints, an API/command or approval boundary.
- What counted as acceptance, and what changed after real feedback?

### AI-assisted engineering control

- What did you delegate to a Coding Agent, and what decisions stayed yours?
- How did you structure repository context and success/acceptance criteria?
- Show an incorrect AI-generated implementation you caught and how you fixed or constrained it.
- Can you navigate the relevant implementation, trace data flow and reproduce a bug?
- How did tests, manual verification and user acceptance differ?

### System and implementation depth

- What does the main data model look like and what invariants must remain true?
- How are authorization, idempotency, audit, errors and retries handled where applicable?
- What would fail with malformed inputs, concurrent actions or unavailable dependencies?
- Which tests cover the critical path? What is not tested?
- What changes would be required for production deployment, privacy and larger scale?

### Provenance and contribution

- What was original design versus an external framework, template or upstream project?
- What was built personally, contributed by colleagues, or generated by coding tools?
- What can be shown publicly and what must stay confidential?
- What material evidence would best demonstrate ownership without exposing private customer data?

### Role-fit stress test

- Which responsibilities would you own confidently in this particular role?
- Which responsibilities would require support from a stronger specialist?
- What limitations would affect delivery in the first 90 days?
- Which key JD requirement has the weakest current proof, and how could it be tested?

## 4. One live exercise

Offer an exercise matched to the role, not an arbitrary puzzle. Example for a product/solution-facing Agent role:

> "A finance department wants an AI assistant to review reimbursement claims. Design a safe, testable first version."

Ask for users, source data, deterministic rules vs model judgments, permission boundaries, human approval, failure cases, audit and observable acceptance conditions. Evaluate the reasoning and decision boundaries, not just the vocabulary.

For roles dominated by hands-on coding or production ownership, substitute a relevant debugging, code-reading or system-design exercise.

## 5. Suggested interview formats

| Duration | Reasonable structure |
| --- | --- |
| **30 min** | 5m role framing + 10m one real workflow + 8m ownership/technical verification + 5m fit/gaps + 2m questions |
| **45 min** | 5m role + 10m business delivery + 10m current project walkthrough + 10m practical design/debugging + 5m limitations + 5m Q&A |
| **60 min** | 5m framing + 15m project evidence + 15m live role exercise + 10m system depth + 10m collaboration/AI review loop + 5m Q&A |

Adapt to what has already been established; do not ask the same generic questions across every round.

## 6. Interview outcome

Report separately the evidence-backed strengths, demonstrated limitations, still-unknown high-impact areas and fit for this **specific** JD. If useful, discuss dimensions rather than compressing everything into a single numerical score.

The strongest question is the one whose answer would most change the hiring or collaboration decision. Protect privacy: ask for sanitized demonstrations, synthetic data or architecture walkthroughs rather than confidential client, student or medical records.
